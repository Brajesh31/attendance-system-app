# 🧩 System design

## Face representation

The current implementation loads InsightFace using `FaceAnalysis(name='buffalo_sc', root='insightface_model', providers=['CPUExecutionProvider'])`. The registration code assumes a 512-element embedding and serializes the mean vector as float32 bytes.

This makes the Redis record dependent on the selected model, preprocessing behavior, embedding dimension, dtype, and serialization conventions. Any model or pipeline change should be versioned. Existing records should not be mixed with embeddings generated by a different model without a controlled migration.

## Similarity search

For registered vectors (x_i) and a query vector (q), the code computes cosine similarity:

```text
cosine(x, q) = (x · q) / (||x|| × ||q||)
```

A candidate is eligible when its score is at least the configured threshold (currently 0.5 in the page call). The highest-scoring eligible row is selected. If no row qualifies, the result is `Unknown`.

The threshold is a demonstration parameter, not a calibrated security boundary. It must be evaluated on representative, consented data. Consider false acceptance and false rejection separately. A threshold that looks good on a handful of examples is not reliable evidence.

## Registration aggregation

For the captured sample matrix (X in mathbb{R}^{n 	imes 512}), the code computes a coordinate-wise mean:

```text
embedding_mean = mean(X, axis=0)
```

There is no explicit quality weighting, outlier removal, sample minimum, normalization step after averaging, or verification that the samples are from one person. These are potential design improvements, not current behavior.

## Attendance event generation

The live page attempts to flush buffered detections every 30 seconds. Within a buffer, duplicate names are dropped, then records are pushed to the left of a Redis list. The string contract is:

```text
Name@Role@Timestamp
```

This event is an observation event, not an authoritative clock-in or clock-out event. The list can contain repeated sightings across windows. Reports infer first and last observation in a day, which can materially differ from actual arrival and departure.

## Reporting algorithm

The report code:
1. Reads the full attendance list with `LRANGE`.
2. Decodes bytes as UTF-8.
3. Splits each record into three fields.
4. Parses the timestamp using pandas.
5. Groups by date, name, and role.
6. Computes minimum and maximum observed timestamps.
7. Calculates elapsed hours/minutes.
8. Uses a 60-second observed span as its present/absent threshold.

The 60-second heuristic is not an approved attendance policy. Report results should be labeled as inferred observations until a proper attendance event model exists.

## Proposed next-generation event model

Use structured fields instead of delimiter-based values:

| Field | Purpose |
|---|---|
| `event_id` | Unique idempotency key |
| `subject_id` | Pseudonymous internal person identifier |
| `event_type` | `observation`, reviewed `check_in`, or reviewed `check_out` |
| `observed_at` | UTC timestamp with explicit timezone |
| `source` | Camera/terminal identifier |
| `model_version` | Face model and pipeline version |
| `review_status` | Pending, accepted, rejected, corrected |
| `created_at` | Ingestion timestamp |

Do not store raw embeddings in routine event payloads. Keep identity mapping and biometric templates behind separate access policies. Add retention expiry and deletion tracking.
